# Client App Mirror — up-to-date Prod mirror for Yannick's Client App

*Created 2026-07-08 (Fred-approved; design passed a two-agent adversarial audit the same day).
Supabase project **`mjxjhwxktedrrnochwli`** ("Client App Mirror"), org Unclogme, us-east-1.
Bills ~$10/mo (Micro compute — the org is Pro, so there are no free projects).*

## What it is

A **continuously-refreshed mirror** of Prod's client-domain tables, for Yannick to build the
**Client App** (Lovable) against real, current data with **zero Prod risk**. Prod is never written —
every Prod access in the pipeline is read-only (Management-API reads use `read_only: true`;
data reads are plain REST GETs).

- **Refresh**: [`scripts/sync/refresh_client_mirror.js`](../../scripts/sync/refresh_client_mirror.js),
  run hourly by [`client-mirror-refresh.yml`](../../.github/workflows/client-mirror-refresh.yml)
  (cron `23 * * * *` + manual `workflow_dispatch`). Full-snapshot upsert per table (self-healing) +
  **scoped delete-missing** + column-drift healing + parity check. Non-zero exit on any parity
  failure / Prod read error / circuit-breaker trip.
- **One-time setup** was `node scripts/sync/refresh_client_mirror.js --setup` (DDL + seed 42,439
  rows across 19 tables + sequence offsets). Re-running setup is safe (CREATE IF NOT EXISTS) but
  should not be needed.
- **Creds**: `Supabase/.env` (gitignored) → `CLIENT_MIRROR_REF/URL/SECRET_KEY/PUBLISHABLE_KEY/DB_PASS`.
  GH secrets: `CLIENT_MIRROR_URL`, `CLIENT_MIRROR_SECRET_KEY`. The project has both legacy and
  new-format keys; we use `sb_secret_…` (server) / `sb_publishable_…` (app).

## Mirrored tables (19)

clients, properties, client_contacts, client_locations, client_groups, service_configs, gdos,
zones, visits, jobs, invoices, line_items, employees, vehicles, visit_team, visit_assignments,
visit_locations, entity_source_links, service_line_items.

**Deliberately NOT mirrored**: `webhook_tokens` (OAuth secrets — never mirror), webhook/event logs,
photos/photo_links/photo_classifications, all `derm_*` + manifest tables, municipality_regulators
(.gov contacts), inspections, reviews. **Excluded columns**: `employees.email`, `employees.phone`
(PII off the permissive-anon sandbox).

## Design rules (why the mirror looks like this — audited)

1. **PK constraints only.** No secondary/partial UNIQUE indexes (a Prod value-swap like a
   client-code renumber would raise transient 23505 during chunked upserts), no FKs (refresh-pattern
   sandbox rule), **no triggers** (`updated_at` arrives as Prod data; no jobber-push can ever fire
   from the mirror).
2. **Identity → plain bigint + local sequence** (`GENERATED BY DEFAULT` semantics) so explicit-id
   upserts from Prod always work.
3. **Sequences offset**: set once at seed to `prod_max + 1,000,000` (per-table threshold stored in
   `public.mirror_meta`). Everything **below** the threshold is Prod-origin; everything **above** is
   test data.
4. **Scoped delete-missing** (Prod hard-deletes are frequent — 961 visits / 838 visit_assignments in
   90d): each run deletes mirror rows that vanished from the Prod snapshot, but **only below the
   threshold**. Circuit breakers: any Prod read error, or a snapshot < 80% of the mirror's
   below-threshold count, skips deletes and fails the run.
5. **Drift healing**: new Prod columns are ADDed to the mirror **as NULLABLE** (never NOT NULL) +
   `NOTIFY pgrst`; Yannick's own added columns are never touched; Prod-dropped columns are logged
   for manual cleanup (tracked via `mirror_meta.prod_columns`).
6. **Custom-function defaults stripped** (only whitelisted defaults copied); `visits.public_id`
   gets a local `substr(md5(random()::text),1,10)` substitute.
7. **RLS**: enabled on every table with permissive anon/authenticated policies (internal build
   sandbox, ship-first house pattern); `statement_timeout = 15s` for anon/authenticated.

## Rules for Yannick (the Client App)

- **Read `v_visits_live`, not `visits`** — the mirror carries soft-deleted visits as-is (375+ rows
  with `deleted_at` set), exactly like Prod.
- **Test data**: just INSERT — default ids land above the threshold and survive every refresh.
  **Edits to Prod-origin rows are reverted within the hour** (it's a mirror). To experiment with a
  real row, copy it into a new row (new id) first.
- Connect the Lovable app with `CLIENT_MIRROR_URL` + the **publishable** key. (supabase-js accepts
  `sb_publishable_…` as a drop-in anon key; smoke-test on first connect.)
- `public.mirror_meta.last_refresh_at` = data freshness; the app can display it.

## Ops

- **Freshness check**: `gh run list --workflow client-mirror-refresh --limit 1` — investigate if the
  last success is >3h old (GitHub can also disable crons after 60d repo inactivity). Or check
  `mirror_meta.last_refresh_at`.
- Manual run: `gh workflow run client-mirror-refresh` or locally
  `cd Supabase && node scripts/sync/refresh_client_mirror.js`.
- The workflow must never gain `pull_request`/`pull_request_target` triggers (public repo; fork PRs
  get no secrets under schedule/dispatch-only triggers).
- When the Client App ships to Prod (per plan-notes item 6: Calendar-style two-way Jobber sync),
  the app repoints to a per-app schema on Prod and this mirror retires or becomes staging.
