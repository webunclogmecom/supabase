## 2. The lightbox took three attempts, and my first two diagnoses were both wrong

**Fred:** *"i can't close the image because even though it have an X closing icon, when clicked on
it, it also closes the modal for editing the job, and if i click on the background (black overlay)
it does nothing."*

Two prompts blamed **event propagation**. Both were wrong. The real cause, found only once I read
the compiled bundle and instrumented the live event path:

**The lightbox layer computed `pointer-events: none`, so no mouse event ever hit-tested to it.** The
handlers were correct the whole time and were simply never invoked. The Edit-job dialog is a Radix
modal, `DismissableLayer` sets `document.body.style.pointerEvents = "none"`, that property is
**inherited**, and the lightbox portals to `body`. Radix re-enables pointer events on its own layers
only.

⚠ **My earlier portal fix CAUSED this.** Moving the lightbox out of the Dialog subtree correctly
stopped it closing the parent — and landed it where it inherits `none`. A correct fix created the
next bug.
⚠ **Escape kept working because keyboard events do not hit-test.** That asymmetry was the whole
tell, and it is what made this look like propagation for two rounds.

Fred human-verified all four close paths. (`fa64623`, `c9a18e8`.)

## 4. Manual GDO filing — the main thread of the two days

**Fred:** *"what if we do that report manually, where can we submit it? nowhere, so we need to have a
manual way to do it at the DERM App"* — then, after the first build: *"i told you only for the ones
with line item 27, make it so it's every visit instead, SC or SA doesn't matter, with or without

Shipped end to end: `fn_record_manual_gdo_report` (SECDEF, **service_role only**), the edge function
`record-manual-gdo-report`, `derm.visit_gdo_manual_eligibility`, `derm.visit_gdo_our_record`,
`filed_by_email` + `is_manual` on `derm.visit_gdo_report`, and the DERM App card, empty state, modal
and "Filed manually" badge.

**Ordering is load-bearing: the edge function uploads the evidence FIRST and calls the RPC LAST.**
It cannot be an app-side write, and the reason is the storage policy: `rpa_evidence_staff_insert`
calls `fn_is_gdo_evidence_path`, which only accepts a path matching an **existing** live submission
row. So `authenticated` physically cannot upload before the row exists, which forces row-first — and
row-first is the dangerous order, because the row is what suppresses the bot.

### Five holes I found in my own work, each before it shipped

| # | what | how it was caught |
|---|---|---|
| 1 | `REVOKE ... FROM PUBLIC` left the `authenticated` grant intact, so the RPC was callable from a browser | read `has_function_privilege`, not the SQL I had written |
| 2 | the screenshot path was validated by **shape only**, so an invented path would commit a filing with no evidence | asked what the regex actually proves |
| 3 | the duplicate check was per **visit**; the queue excludes per **permit**, so a 2-permit property could never be fully recorded | read `v_derm_portal_queue` instead of assuming |
| 4 | the permit was resolved with an unordered `LIMIT 1` — wrong for **44%** of eligible visits (12 of 27 carry 2-3 permits) | visit 5786, my own happy-path test visit, carries **three** permits and its page shows one |
| 5 | a failed bot attempt blocked the manual path, locking the feature out of its own use case | visit 6617's four `ERROR_LOGIN_FAILED` runs |

Hole 4 is the one that would have been worst: recording the wrong permit is worse than recording
nothing, because the row still suppresses the bot while the permit actually filed looks handled.

### Verification

`manual_gdo_filing_guards.sql` (12 cases), `manual_gdo_permit_choice.sql` (5 cases, including that
the **stored** permit equals the chosen one), and `manual_gdo_view_matches_rpc.sql`, which calls the
real function on **every** completed code-27 visit and compares it with what the view predicted —
all 34 agree, 29 yes / 5 no, and it refuses to report success unless both branches were exercised.

### Fred's question, answered with a control

*"what happens when we do it manually, in case the bot also decides to do it, does it replace the
ones we did? does the bot receive on the queue even the ones we do manually?"*

A manual filing removes it from the queue **permanently** — proven by clearing a visit, **watching
it enter the queue**, filing, and watching it leave, then confirming the exclusion came from the
already-reported test rather than the 20h cooldown. The bot only inserts, never updates, so ours is
never replaced.
